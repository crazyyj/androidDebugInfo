# 需求理解 — 三方依赖形态下的宿主字段 / 方法监控（v2）

> 场景：`lib_debug_monitor` 以 AAR 形式被宿主 App 依赖，宿主传入自己的类与字段，SDK 对其数据做监控。
> 硬约束：Release 包（`minifyEnabled true`、非 debuggable）有效；普通 App 权限（无 root、无 Xposed）；`minSdk 23`，尽量覆盖到 Android 16。

## 0. 修订记录

| 版本 | 日期 | 方案 | 触发原因 |
|---|---|---|---|
| v1 | 2026-10-24 | 注解 + Gradle 插件 ASM 插桩 | — |
| **v2** | **2026-10-26** | **运行时 Hook：ShadowHook 作内联引擎 + LSPlant 作 ART 层** | 需求方确认 §9 五问，**不增加 Gradle 插件** → v1 的插桩路线整体出局 |

需求方对 v1 §9 的确认（原文，作为本文约束）：

1. **不增加 Gradle 插件。**
2. **要写事件；读不拦字段**，读要的是「方法被调用的时机」。
3. **不长期持有**，用 `WeakReference` 即可。
4. **暂不考虑跨进程。**
5. **`minSdk` 23。**

---

## 1. 结论

1. **ShadowHook 不是 Java Hook 库。** 它只有 native 函数级 C API（`shadowhook_hook_sym_name` / `shadowhook_hook_sym_addr` / `shadowhook_hook_func_addr`），没有 `java.lang.reflect.Method` 层接口，也没有 `beforeCall` / `afterCall`。它 hook 的是「一段机器码的地址」。
2. **只用 ShadowHook 做「方法进入/退出监听」，会踩 8 个硬坑**（§3），其中 3 个无解。所以它不能单独作为方案，只能是**引擎**。
3. **正确形态是 `LSPlant`（ART 层）+ `ShadowHook`（内联引擎）**。这不是我的组合创新，是 LSPosed 自己的做法：`lsplant::InitInfo.inline_hooker` 就是让调用方塞一个内联 Hook 实现进来，社区默认用 ShadowHook 或 Dobby。LSPlant 覆盖 **API 21–37**（Android 5.0–17），`minSdk 23` 无压力，2026-10 仍在维护。
4. **加了 LSPlant 之后，仍然有 3 个不可消除的缺口**（§4）：字段直写看不到、R8 内联让 Hook 点消失、关闭态开销不为零。这三条是无插件路线的固有代价，不是实现水平问题。
5. **好在需求 2 帮了大忙**：读只关心「方法被调用的时机」，不要求拦截 `GETFIELD`。这砍掉了整个「字段读插桩」的高频灾难，也让主路径可以简化为「**hook 方法边界 + 在边界快照字段**」，而不是「hook 每个字段的访问器」。

## 2. 现有实现审计（v1 结论保留，仍然成立）

| 现有实现 | 能力 | Release 有效 | 结论 |
|---|---|---|---|
| JVMTI（`DebugStackMotionAgent`，`lib_debug_core/src/main/cpp/jvmti.cpp`） | 方法栈进出 + 字段修改，**精确** | ❌ 需 `android:debuggable` | 保留为 debug 增强，能力上限高于本方案 |
| `FieldMonitorHandler` 反射快照轮询 | 值变化（代理方法边界上） | ✅ 但漏、慢、脆 | **本方案的主路径要复用它，先修 bug** |
| `SandHookManager`（反射探 `com.swift.sandhook.SandHook`） | 理论上方法 hook | ⚠️ | 死路径，删除（§2.2） |

### 2.1 `FieldMonitorHandler` 的 10 个问题（v2 里它从「兜底」升级为「主路径」，必须先修）

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| 1 | L71-75 `newProxy()` | `Proxy.newProxyInstance` 要求目标实现接口 | 无接口 / final 类直接抛 `IllegalArgumentException` |
| 2 | L78-82 `invoke()` | 只在「通过代理调用方法」后检查 | 直接字段写、静态方法、其它线程、异步回调全漏 |
| 3 | L92 `getDeclaredField` | 只查当前类不回溯父类 | 继承字段永远 `NoSuchFieldException` |
| 4 | L97-99 | 双 null 时 `return` | **中断整个字段循环**，后续字段全跳过，应为 `continue` |
| 5 | L100-104 | `oldValue != null && newValue == null` 走 `!newValue.equals(...)` | **必现 NPE** |
| 6 | L62 `removeMonitorField` | 判定 `length > 1` | 单字段移除永不生效，应为 `> 0` |
| 7 | L33/L92 | 每次事件都 `getDeclaredField` + `setAccessible` | 无缓存，字段多时压垮主线程 |
| 8 | L71-75 | 每次调用新建 Proxy，不缓存 | 全类扫描/绑定场景对象爆炸 |
| 9 | L23 | 未区分静态 / 实例字段 | 静态字段靠 `field.get(obj)` 侥幸可用，语义混乱 |
| 10 | — | 数组元素 `arr[0]=x`、集合 `list.add(x)` | 字段本身未变，**永远检测不到** |

`FieldManager`（L28-42）另有 2 个问题：

- `mMonitorHandlers` 用 `HashMap<Object, ...>` → 走 `equals/hashCode`，两个内容相等但不同的实例被当成同一个宿主。应改 `IdentityHashMap`（**同时天然满足需求 3：键是强引用，值是弱引用，需要显式处理**，见 §7.2）。
- `setChangeListener` 只在「新建」分支调用，重复 `monitorField` 时新 listener 被静默丢弃。

### 2.2 `SandHookManager` 应删除

- 全程 `Class.forName("com.swift.sandhook.SandHook")` 反射，工程里并没引入 SandHook。
- L120-127 找的 `setHookHandler` 在 SandHook 公开 API 里不存在，即便引入也 `NoSuchMethodException`。
- SandHook 版本覆盖停在 Android 12 附近，2026 年不作为生产依赖。

结论：整条路径移除，不要在其上继续投入。

### 2.3 `MethodFieldMonitorPlugin` 可复用

`setWatchFieldKeys` / `addWatchField` / `sWatchMethodKeys` / `sWatchClassPrefixes`（「全类名#字段名」配置模型）、`mEventLogs` / `MAX_FLUSH_BATCH=80` / 300 条上限、批量 flush，全部可以直接复用。v2 只是把**事件来源**从 JVMTI 换成运行时 Hook。

## 3. ShadowHook 单用的问题（本文重点）

前提：ShadowHook 是**内联 Hook**。它做的事是：拿到目标函数首地址 → 备份首部 4~16 字节到 trampoline（做 PC 相对寻址重定位）→ 用一条 `B`/`BL` 覆盖首部 → 刷 i-cache。所以它只对「**有独立机器码入口、入口长度够放跳转**」的函数有效。

### 3.1 八个坑

| # | 问题 | 具体表现 | 有解？ |
|---|---|---|---|
| 1 | **解释器入口是全进程共享的** | 未编译的方法，`ArtMethod.entry_point_from_quick_compiled_code_` 指向 `art_quick_to_interpreter_bridge`，**所有未编译方法同一个地址**。你在这个地址上 inline hook，等于给进程里所有解释执行的方法统一插一脚；unhook 一起撤。release 包 AOT 只编译带 profile 的热点方法，**绝大多数方法走解释器** | ⚠️ 只能先强制编译（`Jit::CompileMethod` + `kAccCompileDontBother`），代价是常驻内存 + 改变宿主行为 + 编译失败的方法仍然无解 |
| 2 | **JNI native 方法 / 代理方法 hook 不到** | 这两类的 entry 固定指向 `art_quick_generic_jni_trampoline`（同样共享），本身没有 Java 编译产物 | ❌ hook Java 层无解（但要 hook native 方法对应的 C 函数，反而用 ShadowHook 最直接） |
| 3 | **方法太短放不下跳转** | arm64 的 4 字节 `B` 有 ±128MB 限制，超出就要 12~16 字节；而简单 getter/setter 编译后就 3~4 条指令（`LDR`/`STR`/`RET`），arm32 thumb 更紧张 | ⚠️ ShadowHook 会用 ELF LOAD 段空隙放 trampoline 缓解，但极短函数仍可能失败 |
| 4 | **JIT 重编译让 Hook 静默失效** | JIT 热点重编译后 ART 把 entry 换成新地址，你的 patch 还留在旧代码上，永远不被执行。表现为「跑一会儿就不上报了」 | ⚠️ 必须设 `kAccCompileDontBother`(0x02000000) 禁掉该方法的重编译，**永久损失该方法 JIT 优化，且不可逆** |
| 5 | **调用约定要自己实现** | quick entry 的入参是 `x0 = ArtMethod*`、`x1 = Thread*`，之后才是 Java 参数；`long/double` 占两个寄存器槽，`float/double` 走 `v` 寄存器，超 8 个参数落栈。要拿 `this`、拿参数、改返回值，得写 arm32(thumb)/arm64 两套汇编 trampoline 并按签名分派 | ❌ 这是 Pine `beforeCall/afterCall` 帮你做完的部分，自己做 ≈ 重写半个 Pine |
| 6 | **「退出」和返回值拿不到** | inline hook 只改函数入口，改不了方法体内每条 `IRETURN/.../RETURN`，所以异常路径、多 return 点都只能靠「调原函数前后读 `Thread::GetException()`」推断；而 TLS 槽位偏移（`__get_tls()[TLS_SLOT_ART_THREAD_SELF]`）跨版本有差异，reference 返回值还涉及 read barrier / 局部引用表 | ⚠️ 可做，但脆弱 |
| 7 | **ArtMethod 结构偏移要自己维护** | `entry_point_from_quick_compiled_code_`、`access_flags_`、`declaring_class_` 的偏移在 5/6/7/8/11/12/13/14 每代都动过（12 起 hotness 并入 access_flags）。要写 6+ 套判定 | ⚠️ 每次新系统还要跟，长期维护成本高 |
| 8 | **可检测性比入口替换高一个量级** | 入口替换只改 `ArtMethod` 里一个指针，内存里代码页和磁盘 ELF 完全一致；inline hook 会改动 `.text` 页。风控/加固能扫：函数首部与磁盘 ELF 不一致、`/proc/self/maps` 里 `libshadowhook.so`、`mprotect(PROT_EXEC)` 审计、`kAccCompileDontBother` 异常标志位 | ⚠️ 可静态链接、可改名、可预埋 text 槽位，但不能完全消除 |

另外两个工程性坑：

- **16KB page size**（Android 15+ 部分设备，Google Play 2025-11 起强制）：ShadowHook 的 `.so` 必须按 16KB 对齐构建。旧版 prebuilt 在 16KB 机型上直接加载失败，且报错信息与「不支持的 ABI」很像，容易误判。要用带 16KB 支持的版本。
- **arm64 BTI/PAC**：部分 Android 15+ 产物启用 BTI，跳转目标必须是合法 landing pad，否则 `SIGILL`。自己写的 handler 需要 `-mbranch-protection=bti` 编译。
- **安装时机**：inline hook 要 `mprotect` + 改写代码页，此时若有线程正好执行到该函数首部，会崩（SIGSEGV/SIGILL，且崩在宿主里，日志看不出是我们的问题）。要在进程极早期安装，不能等 UI 跑起来。

### 3.2 一句话

ShadowHook 单独用，等于**从零重写一个 Pine/SandHook**，而且写出来的东西在字段问题上一点都没变好。

## 4. 加 LSPlant 之后：哪些消失，哪些还在

LSPlant 做的是**入口替换 + 内联去优化**（不是 inline hook 目标方法本身，inline hook 只用来 hook libart.so 内部函数）。

| §3 的坑 | 加 LSPlant 后 |
|---|---|
| 1 共享解释器入口 | ✅ 消失。入口替换天然是 per-method，未编译方法也能 hook |
| 2 JNI / 代理方法 | ✅ 消失（`Proxy` 方法也能 hook，因为它替换的是 `ArtMethod`） |
| 3 方法太短 | ✅ 消失（不要求首部长度） |
| 4 JIT 重编译 | ✅ 消失。LSPlant 自带 inline deoptimization，会把已内联的调用方去优化，让调用重新经过 `ArtMethod` |
| 5 调用约定 | ✅ 消失。回调签名固定 `Object callback(Object[] args)`，参数装箱由 LSPlant 处理 |
| 6 退出 / 返回值 | ✅ 消失。回调里 `try { ret = backup.invoke(args) } catch (InvocationTargetException e) { ... }`，返回值与异常都在手 |
| 7 ArtMethod 偏移 | ✅ 消失（LSPlant 自己按版本处理，含 API 21–37） |
| 8 可检测性 | ❌ **仍在**。LSPlant 初始化时要 inline hook libart.so 内部函数，痕迹依然存在 |
| — | ❌ **新引入**：每次调用都要走 stub → JNI → 装箱 → 反射调 backup，**关闭态也不零成本**（见 §6.3） |
| — | ❌ **新引入**：每个 hook 生成一个 stub 类（默认 `LSPHooker_`），hook 数量别上千；类名会出现在堆栈，需 `generated_source_name` 置空隐藏 |
| — | ⚠️ 加固 / 反调试 / 完整性校验的宿主，LSPlant 初始化可能失败甚至崩溃，必须能优雅降级 |

### 4.1 仍然无解的 3 个缺口（跟 ShadowHook 无关，是「无插件」的代价）

1. **字段直写看不到。** `PUTFIELD` 在 arm64 编译成一条 `STR`，**没有任何函数入口**，ShadowHook / LSPlant / Pine / Frida 都 hook 不到。只能 hook 访问器方法。
2. **R8 内联让访问器 Hook 点消失。** `minifyEnabled true` 时 R8 会把小 getter/setter 内联进调用点，调用点退化成直接字段访问 —— 方法还在（被 keep 住），但**没人调用它**。LSPlant 的 deopt 只能撤销 ART 的 JIT/AOT 内联，撤销不了 R8 在 dex 层做的内联。对策见 §6.2（`consumer-rules.pro` 里的 `-neverinline`），代价是宿主全 App 访问器失去内联优化。
3. **关闭态开销不为零。** 插桩方案关闭时是「1 次 volatile 读」；Hook 方案关闭时仍然是完整一次 stub + JNI + 反射。所以 hook 数量必须受控，且要给出明确上限。

## 5. 目标架构

```
lib_debug_monitor（现有 AAR）
├── MonitorApi          宿主入口：传 Class + 字段名 / 传 Method 引用 + 回调
├── TargetResolver      反射解析访问器、缓存 Field/Method、父类回溯、静态/实例区分
├── SnapshotEngine      复用 FieldMonitorHandler 的比对逻辑（先修 5 个 bug），改挂到方法边界
├── hook/               Java 层封装
│   ├── ShadowHookLoader   加载 .so、JNI 注册、初始化 LSPlant
│   ├── LsplantBridge      native: Hook / UnHook / IsHooked
│   └── HookRegistry       id → (hookerObj, backup, 回调)，WeakReference 管理宿主对象
├── native/             cpp
│   ├── lsplant_jni.cpp    InitInfo.inline_hooker 用 ShadowHook 实现
│   └── shadowhook/        预编译 .so（16KB 对齐）
└── 事件通道             复用 mEventLogs / MAX_FLUSH_BATCH / 300 条上限 → app_debug_pc_tools
```

`DebugStackMotionAgent`（JVMTI）保留：debug 包走 JVMTI（字段级精确），release 包自动降级走 Hook。上层 UI 和 PC 通道无差别。

### 5.1 初始化（关键顺序）

```cpp
JNI_OnLoad:
  shadowhook_init(SHADOWHOOK_MODE_UNIQUE, false);   // 进程唯一实例，允许共享 hook

Monitor.install(Context):        // Application.attachBaseContext 之后立刻调
  System.loadLibrary("monitor_hook");
  lsplant::InitInfo info;
  info.inline_hooker   = [](void* target, void* hooker) -> void* {
      void* orig = nullptr;
      shadowhook_hook_func_addr(target, hooker, &orig);
      return orig;                                 // 返回给 LSPlant 当 backup
  };
  info.inline_unhooker = [](void* handle) -> bool { return shadowhook_unhook(handle) == 0; };
  info.generated_source_name = "";                 // 不在堆栈暴露来源
  lsplant::Init(env, info);                        // 失败 → 降级，不崩
```

`inline_hooker` 的具体签名以所用 LSPlant 版本头文件为准（上游 v2 是 `(void* target, void* hooker)`，有分支库改成三参 + 返回 handle）。

## 6. 三类需求怎么落到方法上

### 6.1 主路径：方法边界 + 字段快照（对应需求「读=方法被调用的时机」）

宿主指定「关心哪些方法」，我们在这两类边界上打点，进出各做一次快照比对：

```java
Monitor.watchBoundary(UserModel.class, "refresh", snapshotFields("age", "name", "level"), cb);
```

```
onEnter(id, receiver):  在监控表里按 identity 记下所有字段当前值（浅拷贝，primitive 直接存）
onExit (id, receiver):  再读一遍，逐字段比对，差异逐条上报 WRITE 事件
```

- 一次 Hook 覆盖该方法**及其所有同步子调用**内的字段变化，不需要为每个字段建 Hook → **hook 数量 = 方法数，不是字段数**，这是本方案能用的关键。
- 复用 `FieldMonitorHandler.checkProperty()` 的比对逻辑，但入口从「Proxy 调用后」换成「Hook 的 exit」，顺带修掉 §2.1 的 #1（无需接口）、#2（直写也能被 exit 快照抓到）、#3~#10。
- **漏的场景必须写进对接文档**：方法返回之后在别的线程改字段、方法内部中间态、纯静态初始化里的赋值。debug 包用 JVMTI 能拿到精确的字段写，release 包拿不到 —— 这是能力差异，不是 bug。

### 6.2 补充路径：访问器 Hook（要「每一次写」的精确实时事件时）

```java
Monitor.watchWrite(UserModel.class, "age", cb);   // 解析 setAge(int) 后 hook
```

宿主侧必须配 `consumer-rules.pro`（由我们的 AAR 携带，不是 Gradle 插件，宿主无感）：

```proguard
# 1) 阻止 R8 内联访问器，否则 Hook 点不存在
-neverinline class ** {
    void set*(...);
    *** get*();
}
# 2) 保注解与成员名，否则运行期按名字找不到字段
-keepattributes RuntimeVisibleAnnotations
-keepclassmembers,allowoptimization class ** {
    @com.newchar.debug.monitor.annotation.WatchField <fields>;
}
```

限制必须提前说明（否则对接方一定踩）：

| 场景 | 能否监控 | 原因 |
|---|---|---|
| Kotlin `var` / JavaBean 外部访问 | ✅ | 必经 `get/set` |
| 同类 / 同包内直接读写字段 | ❌ | 直接 `GETFIELD/PUTFIELD`，不经访问器 |
| `public` 裸字段、`@JvmField`、`lateinit var` | ❌ | 无访问器 |
| `data class.copy()` | ❌ | 走构造器，不写字段 |
| 构造器内赋值 | ❌ | 无 setter |

**结论：6.2 只能作为 6.1 的补充，别单独用。** 6.1 是「值变了告诉我」，6.2 是「谁在什么时候写的」。前者覆盖面广，后者精确但覆盖窄。

### 6.3 关闭态的成本

Hook 是方法级整体替换，**没法定点短路**：`ENABLED == false` 时依然要走 stub → JNI → 装箱 `Object[]` → 反射调 backup。经验量级：单次 1~10 μs，是普通方法调用的 100~1000 倍。

所以：

- 只 hook 宿主显式指定的方法，**建议上限 50 个**，超过要警告；
- 关闭监控用 **unhook** 而不是靠开关，但 unhook 后重开会丢已捕获的旧值快照；
- 明确禁止 hook `onDraw` / `onBindViewHolder` / `getView` / `toString` / `equals` / `hashCode` 这类高频方法，注册时按方法名 + 是否 override 做黑名单拦截。

## 7. 运行时契约

### 7.1 事件模型

```
Event { id, kind(ENTER|EXIT|WRITE), tid, tsNanos, hostRef, fieldName, oldValue, newValue, throwable }
```

`READ` 类型删除（需求 2 已确认不做字段读拦截）。

### 7.2 宿主对象引用（需求 3：WeakRef）

- `HookRegistry` 用 `WeakReference<Object>` 存宿主对象，`ReferenceQueue` 清理；
- key 必须是 `System.identityHashCode` + `IdentityHashMap`，不能用 `equals`；
- **注意**：LSPlant 的 `hooker_object` 是强引用，它持有的是 backup `Method`，不含宿主实例，安全；但回调里拿到的 `receiver` 不要塞进事件队列，只放 `{类名, identityHash}`，需要值就在回调线程内序列化成 primitive/String 再入队；
- 快照表（`onEnter` 记的值）同样是弱键，宿主对象被回收后随之清理，否则长跑必 OOM。

### 7.3 递归防护

- 回调内如果读写了被监控对象，会再次进 hook（LSPlant 每个 hook 有 stub，递归会叠加）。用 `ThreadLocal<int> depth`，`depth > 0` 直接调 backup 透传；
- 回调内**禁止**做序列化 / IO / 反射二次解析；
- 分发走独立线程 + 批量队列，不在被监控线程里 flush。

### 7.4 与 PC 工具对接

复用 `MethodFieldMonitorPlugin` 的 `mEventLogs` / `MAX_FLUSH_BATCH=80` / 300 条上限。只是把来源从 JVMTI 换成 Hook，UI 不重写。

## 8. R8 / 混淆

| 问题 | 处理 |
|---|---|
| 运行期按字符串找字段 / 方法 | 靠 §6.2 的 `-keepclassmembers` 保名；更稳的做法是让宿主传 `Method` 引用（`UserModel::setAge`），编译期绑定，天然抗混淆 |
| `-adaptclassstrings` 改写类名字符串 | 不用字符串承载标识，用 `identityHashCode` / int id |
| 访问器被内联 | `-neverinline`（§6.2） |
| 访问器被裁掉 | `-keepclassmembers`；但被裁掉通常意味着真没人调用，裁掉也无所谓 |
| `MonitorApi` 自身被裁/内联 | `consumer-rules.pro` 加 `-keep class com.newchar.debug.monitor.** { *; }` |
| LSPlant 反射回调找不到 | `-keepclassmembers class * { public java.lang.Object callback(java.lang.Object[]); }` |
| 需要「按混淆后类名反查」 | 构建后读 `mapping.txt` 生成反向索引打 asset，与 v1 同 |

## 9. 风险与可检测性

1. **加固 / 反调试宿主**：360 加固、腾讯乐固、以及带完整性校验的风控 SDK，可能在 LSPlant init 阶段崩溃或触发风控。必须 try/catch + 初始化探针，失败就降级为「仅 debug 包可用」并向宿主提示。
2. **可检测痕迹**：`libshadowhook.so` 在 maps 里、`.text` 页有 patch、`ArtMethod` 有 stub、堆栈有 `LSPHooker_`。面向 C 端的产品要评估过审风险（应用市场与 Play Integrity）。
3. **崩溃归因**：任何 inline hook 崩溃都发生在宿主进程里，客户第一时间会指我们。要在 `Init` 前后加埋点，且首次 hook 失败时必须**不抛异常**，只记一条「该目标不支持」。
4. **License**：ShadowHook 是 MIT；**LSPlant 是 LGPL-3.0**。以 AAR 动态链接分发通常可行，但需附许可声明、并保证用户可替换该 `.so`。商业闭源 SDK 请法务确认。
5. **`libc++_shared.so` 冲突**：作为 lib 被三方依赖时，宿主可能已带别的 `libc++_shared.so` 版本。用 `lsplant-standalone` 变体可规避。
6. **测试面收窄**：只在 arm64 真机可靠；x86_64 模拟器与 arm translation 下 LSPlant 不稳。CI 必须真机。

## 11. 原 §9 五问的答案 → 对设计的影响

| 原问题 | 确认答案 | 设计影响 |
|---|---|---|
| 1. 宿主是否允许加 Gradle 插件 | **不允许** | 插桩方案整体出局；字段直写永久不可见；改为 Hook 访问器 + 方法边界快照；`consumer-rules.pro` 成为唯一能影响宿主构建的手段（它不是插件，但会略微降低宿主全 App 访问器内联率，需提前告知） |
| 2. 只要写变化，还是也要读 | **要写；读只要「方法被调用的时机」** | 删除 `READ` 事件与读采样机制；主路径变成方法边界快照（§6.1），hook 数量 = 方法数而非字段数，性能可控 |
| 3. 宿主对象生命周期 | **不长期持有，`WeakRef` 即可** | `HookRegistry` 用 `WeakReference` + `ReferenceQueue`；事件只带 `{类名, identityHash}`，不带实例；快照表弱键 |
| 4. 是否跨进程 | **暂不考虑** | 只初始化主进程；多进程宿主里非主进程不监控，需在文档写明；`id` 表不做重建机制，`Monitor.install` 里加 `processName` 判断 |
| 5. `minSdk` | **23** | LSPlant 21+ / ShadowHook 16+，均满足；`Unsafe` / `VarHandle` 不可用（26+），字段直写只能走 `Field.set` 或 backup 反射；desugaring 无额外要求 |

## 12. 不建议做的事

- **不要单用 ShadowHook 直接 hook `ArtMethod` entry。** 解释器入口共享这个坑绕不过去，等于重写 Pine（§3）。
- **不要指望 LSPlant 的 deoptimization 解决 R8 内联。** 它只能撤 ART 的 JIT/AOT 内联，撤不了 dex 里的静态内联，必须靠 `-neverinline`。
- **不要用入口替换去 hook 字段。** `ArtField` 没有可替换入口，只有反射读写（是取值，不是 Hook）。
- **不要在 AAR 里塞 ASM 运行期改宿主 dex。** 宿主 dex 已加载进 ART，不支持热替换方法体。
- **不要 hook 高频方法。** 关闭态也要走 JNI + 反射，`onDraw` 级别的方法会直接卡死界面。
- **不要用 `HashMap` 存宿主对象。** `equals` 会把两个内容相等的实例当成同一个（§2.1）。
- **不要在 `Init` 失败时抛异常。** 宿主是三方 App，崩溃归因到我们。
