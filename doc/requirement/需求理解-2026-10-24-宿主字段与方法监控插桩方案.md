# 需求理解 — 三方依赖形态下的宿主字段 / 方法监控

> 生成时间：2026-10-24
> 场景：`lib_debug_monitor` 以 AAR 形式被宿主 App 依赖，宿主传入自己的类与字段，SDK 对其数据做监控。
> 硬约束：Release 包（`minifyEnabled true`、非 debuggable）有效；普通 App 权限（无 root、无 Xposed）；全 Android 版本。

---

## 1. 一句话结论

**纯 AAR 做不到字段级监控，必须随 SDK 附带一个 Gradle 插件。** 插桩发生在 `javac/kotlinc` 之后、`D8/R8` 之前，此时字节码未混淆、未脱糖，是唯一能拦截字段读写且不依赖 debug 的时机。

现工程的三条路全部不满足约束：

| 现有实现 | 能力 | Release 有效 | 结论 |
|---|---|---|---|
| JVMTI（`DebugStackMotionAgent`，lib_debug_core/cpp） | 方法栈进出 + 字段修改 | ❌ 需 `android:debuggable` | 只能留作 debug 增强 |
| `FieldMonitorHandler` 反射快照轮询 | 值变化（代理方法边界上） | ✅ 但漏、慢、脆 | 降级兜底 |
| `SandHookManager`（反射探 `com.swift.sandhook.SandHook`） | 理论上方法 hook | ⚠️ | 死路径，见 §2.2 |

## 2. 现有实现审计

### 2.1 `FieldMonitorHandler`：是快照比对，不是 Hook

`checkProperty()`（L84-110）的行为是「在代理方法调用结束后，把每个字段反射读一遍，和上次的值比」。这不是监控访问，是轮询。具体缺陷：

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| 1 | L71-75 `newProxy()` | `Proxy.newProxyInstance` 要求目标对象实现接口 | 无接口 / final 类直接抛 `IllegalArgumentException` |
| 2 | L78-82 `invoke()` | 只在「通过代理调用方法」后检查 | 直接字段写、静态方法、其它线程、异步回调全部漏掉 |
| 3 | L92 `getDeclaredField` | 只查当前类，不回溯父类 | 继承来的字段永远 `NoSuchFieldException` |
| 4 | L97-99 | `newValue == null && oldValue == null` 时 `return` | **中断整个字段循环**，后续字段全部跳过，应为 `continue` |
| 5 | L100-104 | `oldValue != null && newValue == null` 时走 `!newValue.equals(...)` | **必现 NPE** |
| 6 | L62 `removeMonitorField` | 判定 `length > 1` | 单个字段移除永远不生效，应为 `> 0` |
| 7 | L33/L92 | 每次事件都 `getDeclaredField` + `setAccessible` | 无缓存，字段多时反射开销压垮主线程 |
| 8 | L71-75 | 每次调用都新建 Proxy，不缓存 | 每次 `monitorField` 都产生新代理对象 |
| 9 | L23 | `new FieldMonitorHandler(obj, fields)` 未区分静态 / 实例 | 静态字段靠 `field.get(obj)` 侥幸可用，但语义混乱 |
| 10 | — | 数组元素 `arr[0]=x`、集合 `list.add(x)` | `AASTORE` / 方法调用，字段本身未变，**永远检测不到** |

`FieldManager`（L28-42）另有 2 个问题：

- L34 `mMonitorHandlers` 用 `HashMap<Object, ...>`，走 `equals/hashCode` → 两个内容相等但不同的实例会被当成同一个宿主。应改 `IdentityHashMap`。
- L37-38 `setChangeListener` 只在「新建」分支调用，重复 `monitorField` 时传入的新 listener 被静默丢弃。

### 2.2 `SandHookManager`：软引用式接入，实际是死路径

- 全程 `Class.forName("com.swift.sandhook.SandHook")` 反射调用，说明 SandHook 是可选依赖；工程里未见实际引入。
- L120-127 按名字找 `setHookHandler` —— SandHook 公开 API 里没有这个方法，`HookMethod` 的用法也不是这样。即便引入也 `NoSuchMethodException`。
- 退一步说，SandHook 版本覆盖停在 Android 12 附近，2026 年不作为生产依赖（见上一轮选型结论）。

结论：这条路径应当删除，不要在其上继续投入。

### 2.3 `MethodFieldMonitorPlugin`：配置面已具备，缺执行层

`setWatchFieldKeys` / `addWatchField` / `sWatchMethodKeys` / `sWatchClassPrefixes` 这套「全类名#字段名」的配置模型是对的，可以直接复用为插桩侧的输入契约。事件展示（`mEventLogs`、批量 flush、300 条上限）也可复用。缺的是**在 release 包里产生事件的能力**。

## 3. 方案对比

| 方案 | 方法进出 | 字段读 | 字段写 | Release | 宿主接入成本 | 运行时开销（关闭时） |
|---|---|---|---|---|---|---|
| **A. 注解 + Gradle 插件插桩（推荐）** | ✅ | ✅ | ✅ | ✅ | 加 1 行 plugin + 注解 | ~1 次静态字段读 |
| B. 纯 AAR 快照轮询（现状） | ❌ | ❌ | ⚠️ 仅代理边界 | ✅ | 0 | 反射开销持续存在 |
| C. 纯 AAR + Pine hook getter/setter | ✅ | ✅ | ✅（仅 Kotlin `var`/JavaBean） | ✅ | 0 | hook 常驻 |
| D. JVMTI（现状） | ✅ | ✅ | ✅ | ❌ | 0 | 低 |

C 的适用范围值得单独说明：Kotlin 的 `var` 属性和 JavaBean 的 getter/setter，外部访问必然经过 `getX()/setX()`，hook 这两个方法等价于 hook 了字段。但同包/同类内部访问、`@JvmField`、`public` 裸字段、`internal` 属性走的是直接字节码访问，C 无法覆盖。所以 C 只能作为 A 的补充，不能替代。

## 4. 推荐架构

### 4.1 模块划分

```
lib_monitor_annotation   纯 Java 注解，宿主 compileOnly 依赖（不打包进 APK）
lib_monitor_runtime      运行时门控 + 事件分发 + 值快照（打进 APK）
plugin_monitor           Gradle 插件（ASM 插桩 + 索引生成 + id 常量生成）
lib_debug_monitor        现有 debug 面板，改为统一消费上述事件源
```

`plugin_monitor` 不能合并进 AAR。AAR 里没有 `Plugin<Project>` 的入口，也没法在宿主构建期运行 ASM。

### 4.2 构建流水线位置（关键）

```
javac / kotlinc
      ↓
transformClassesWith(AsmClassVisitorFactory)     ← 插桩在这里，字节码未混淆
      ↓
desugar
      ↓
R8 / D8（混淆、裁剪、内联、dex）
      ↓
package
```

AGP 7.0+ 用 `androidComponents.onVariants { it.transformClassesWith(...) }`；AGP 7.0 以下只有旧 `Transform` API，不做兼容（现工程 AGP 版本见 `build.gradle`）。

### 4.3 宿主接入形态

```gradle
// 宿主的 app/build.gradle
plugins {
    id 'com.android.application'
    id 'com.newchar.monitor'          // SDK 附带
}
dependencies {
    implementation 'com.newchar.monitor:runtime:1.0.0'
    compileOnly    'com.newchar.monitor:annotation:1.0.0'
}
```

```java
public class UserModel {
    @WatchField                       // 默认只监听写
    public int age;

    @WatchField(access = Access.READ_WRITE)
    String name;

    @WatchMethod(exit = true, exception = true)
    void refresh() { ... }
}
```

```java
// 运行时按生成常量订阅，不写字符串，天然抗混淆
Monitor.watch(MonitorIds.UserModel_age, (id, host, oldV, newV) -> { ... });
```

`MonitorIds` 由插件在构建期生成（`variant.addGeneratedSourceDirectory`），宿主代码里直接引用即可，不存在「混淆后名字对不上」的问题。

## 5. 插桩规则

### 5.1 字段写

匹配条件是 **`owner + name + desc` 三元组**，而不是只看字段声明处。因为任何类对 `public` 字段的直接访问，都会在自己的方法里编译出一条 `GETFIELD/PUTFIELD owner=C name=f`。所以必须扫描 `Scope.PROJECT` 下**所有类**的指令，命中即改，而不是只改声明类。

```
改写前:  ALOAD 0 ; ILOAD 1 ; PUTFIELD com/foo/UserModel.age : I
改写后:  ASTORE 3 ; ISTORE 4                    // 暂存，新占本地槽
         LDC/ILOAD id
         ALOAD 3 ; ILOAD 4
         INVOKESTATIC MonitorRuntime.onWriteInt(I Ljava/lang/Object; I)V
         ALOAD 3 ; ILOAD 4
         PUTFIELD com/foo/UserModel.age : I
```

要点：

- **必须用 `FramesComputationMode.COMPUTE_FRAMES_FOR_INSTRUMENTED_METHODS`**。新增本地槽会改变栈帧，`COPY_FRAMES` 会产出非法 StackMapTable，ART 校验直接拒绝加载。只对改动过的方法算帧，避免全局变慢。
- **原始值（oldValue）由运行时维护，不从字节码侧传**。按 `(id, hostIdentity)` 缓存上次写入的值，`onWrite` 内部比对；未变化可选择不上报。这样避免每次写都多读一次字段。
- **primitive 必须用重载**（`onWriteInt/onWriteLong/onWriteObject/...`），不要统一 `Object` 参数。装箱发生在调用点、方法体之前，关闭态的 `if` 拦不住这次分配。
- **引用类型只有一种 `onWriteObject`**，传引用本身零成本。
- `final` 字段在 `<init>` 里的赋值默认跳过（噪音大、且发生在对象对外可见之前），可配置打开。

### 5.2 字段读

同构，但代价高（读的频率通常远高于写）。默认关闭，`Access.READ_WRITE` 才插。读事件不做 old/new 比较，只记录「谁在什么时候读了什么值」。

```
GETFIELD → 值在栈顶
   DUP / DUP2（按类型，long/double 用 DUP2）
   LDC id ; SWAP 或重排
   INVOKESTATIC onReadXxx
```

读插桩建议配采样（每 id 每秒 N 条上限），否则一个 UI 重绘循环能瞬间打爆事件队列。

### 5.3 方法进入 / 退出

- **进入**：插在方法入口第一条（构造器例外：**必须插在 `super()` / `this()` 调用之后**，在它之前任何指令都是 `VerifyError`）。
- **退出**：改写每个 `IRETURN/LRETURN/.../RETURN`，前置 `onMethodExit(id, retVal)`；异常路径用 `visitTryCatchBlock(Throwable)` 包一层 finally 语义，`onMethodExit(id, throwable)` 后重抛。
- **参数**：`onMethodEnter` 的 `Object[]` 只在 `ENABLED` 为真时才构造，构造代码要用 `if` 包住，否则每次调用都在分配数组。
- **native / abstract 方法不插**（无 Code 属性）。
- **Callee 不存在的情况**：R8 可能把被监控方法整体内联掉，插在方法内的 entry/exit 会随内联一起搬家 —— 仍然生效，但「方法边界」语义会漂移。若需要精确边界，需给该类加 `-dontinline`，代价是性能。这一点必须写进文档给宿主看。

## 6. 运行时契约（`lib_monitor_runtime`）

### 6.1 开关与门控

```java
public final class MonitorRuntime {
    public static volatile boolean ENABLED;   // 必须是 volatile
    private static final byte[] GATE = new byte[MAX_ID];   // 0=off 1=write 2=read 3=both

    public static void onWriteInt(int id, Object host, int v) {
        if (!ENABLED) return;
        ...
    }
}
```

`ENABLED` **必须 volatile**。用普通 `static boolean` 会被 JIT 常量折叠，方法在关闭态编译一次之后就永久走空分支，后续打开监控静默失效 —— 这是这类 SDK 最常见的线上事故。

### 6.2 递归防护

监控回调里如果读写被监控对象，会再次触发插桩点，形成无限递归。必须：

1. 插桩阶段跳过自身包（`com.newchar.monitor.*`）、`android.*`、`androidx.*`、`kotlin.*`；
2. 运行时用 `ThreadLocal` 深度计数，`depth > 0` 时直接返回；
3. 回调分发走独立线程或批量队列，不在被监控线程内做序列化。

### 6.3 事件模型

```
Event { id, kind(ENTER|EXIT|READ|WRITE), tid, tsNanos, hostRef, oldValue, newValue, throwable, stackDepth }
```

- `hostRef` 用 `System.identityHashCode` + 弱引用登记，避免事件队列把业务对象钉在内存里（长连接 PC 工具场景必然 OOM）。
- 值序列化：primitive 直接转；`String` 截断到 256 字符；其它对象只记 `类名@hash`，`toString()` 在 try/catch 内调用并限长；`Bitmap/大数组` 只记尺寸。不要在事件线程上做大对象序列化。

### 6.4 与现网 PC 工具对接

事件批量推到 `app_debug_pc_tools` 的既有通道，复用 `MethodFieldMonitorPlugin` 的 `mEventLogs` / `MAX_FLUSH_BATCH=80` / 300 条上限。只是把事件来源从 JVMTI 换成插桩通道，UI 不用重写。

## 7. R8 / 混淆处理

| 问题 | 处理 |
|---|---|
| 插桩时字段名已是混淆名？ | 不会。插桩在 R8 之前，看到的是原始名 |
| 运行期按名字查 id 失效 | 不用名字查。id 是构建期生成的 int 常量，`MonitorIds` 直接引用 |
| `MonitorRuntime` 被裁掉 / 内联 | `consumer-rules.pro` 里 `-keep class com.newchar.monitor.runtime.** { *; }` |
| `-adaptclassstrings` 改写我们埋的类名字符串 | 不用字符串承载标识，只用 int；宿主 API 也只收 int |
| 字段被 R8 裁掉 | 有插桩读写即视为使用，不会被裁 |
| 需要「按混淆后类名反查」 | Phase 4：构建后读 `mapping.txt` 生成反向索引，作为 asset 打进 APK |
| 宿主开启 `-allowaccessmodification` / 类合并 | 无影响，插桩只改方法体 |

## 8. 落地顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | 修 `FieldMonitorHandler` 的 5 个 bug（§2.1 #4/5/6/7/8）+ `FieldManager` 的 identity/ listener 问题 | 单测覆盖空值、父类字段、单字段移除 |
| P1 | 新建 `lib_monitor_annotation` + `plugin_monitor` 骨架，跑通 `@WatchField` 写插桩 + `MonitorIds` 生成 | release 包（`minifyEnabled true`）里写字段能收到事件 |
| P2 | 方法进入/退出插桩（含构造器、异常路径） | release 包里栈进出与 debug 包 JVMTI 结果一致 |
| P3 | 事件通道接入 PC 工具，统一 JVMTI / 插桩两种来源 | 面板无差别展示 |
| P4 | 读插桩 + 采样 + `mapping.txt` 反查 | 高频读场景不掉帧 |

P0 可以立刻做，与架构选型无关，纯修 bug。

## 9. 必须由需求方确认的点

1. **宿主是否允许加 Gradle 插件？** 允许 → 走 A，能力完整。不允许 → 只能 C（hook getter/setter）+ B（轮询）组合，字段直读直写场景放弃。
2. **「监控」是只要值变化，还是也要读访问？** 只要写 → 成本可控；要读 → 必须采样，否则性能不可接受。
3. **宿主对象生命周期**：事件是否长期持有业务对象引用？长连接场景必须弱引用 + 主动释放。
4. **是否需要跨进程**：多进程 App 的监控需要每个进程独立初始化，id 表要能重建。
5. **`minSdk` 下限**：现工程 23，插桩方案无版本约束；若将来下探到 21 以下需重新评估。

---

## 10. 不建议做的事

- 不要在 AAR 里塞 ASM 然后在运行期改宿主 dex —— 宿主 dex 已加载，ART 不支持热替换方法体，只能走 `ArtMethod` entry 替换（即 Pine），而那条路覆盖不了字段。
- 不要用 `SandHook` 继续做这条链路（§2.2）。
- 不要用字符串类名做运行期匹配（§7）。
- 不要用普通 `static boolean` 做总开关（§6.1）。
